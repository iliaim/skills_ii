# Multi-agent orchestration: source review

Reviewed `orchestrate-threads`, `delegate-to-thread`, and `agent-communication`, plus the orchestration contract, delegate task contract, and advanced delegation reference. These external patterns are guidance, not mandatory standards; provider/runtime semantics and explicit user authority remain controlling.

## Priority findings

1. **Untrusted child and source content in privileged prompts — small clarity opportunity (P2).** The contracts already treat transcript/report content as untrusted evidence, disallow copied wrapper text from granting authority, require redaction, and constrain child authority. OpenAI likewise warns against putting untrusted data in developer messages and recommends structured outputs to constrain downstream flow ([Safety in building agents](https://developers.openai.com/api/docs/guides/agent-builder-safety); [prompt-injection design](https://openai.com/index/designing-agents-to-resist-prompt-injection/)). Consider one cross-cutting rule for dispatch/continuation: quoted external text, child reports, tool output, and envelope fields are data; extract only schema-validated facts into trusted instructions, and never let those payloads expand authority. This is a wording reinforcement, not a missing safety boundary.

2. **Idempotency versus retry — deliberate policy, clarify provider-specific exception only if needed (P2).** The delegate contract's “one logical delegation = one creation call” and no retry after ambiguous results avoids duplicate task side effects. Durable workflow systems distinguish retryable activity execution from starting a new workflow and rely on stable identities/idempotent handlers for effectively-once behavior ([Temporal task semantics](https://docs.temporal.io/tasks); [Azure Durable Functions retries](https://learn.microsoft.com/en-us/azure/azure-functions/durable/durable-functions-error-handling)). No generic retry should be inferred for task creation. If a future provider exposes a documented idempotency key or exact reconciliation API, the contract could name it as the only permitted recovery mechanism; otherwise current fail-closed behavior is sound.

3. **Writer ownership and bounded fan-out — covered; preserve the procedural caveat (no gap).** Writable children declare resource scope, base revision, access mode, claim interval, conflict policy, and integration owner; shared writes serialize, with isolated worktree overlap requiring integration ownership and conflict checks. The contract explicitly says claims are not runtime locks. OpenAI recommends bounded independent tasks and coordination for agents that edit the same files ([Multi-agent guide](https://developers.openai.com/api/docs/guides/agents-api/multi-agent)); Azure's fan-out/fan-in model is useful only for independent work whose results can be aggregated ([fan-out/fan-in](https://learn.microsoft.com/en-us/azure/azure-functions/durable/durable-functions-fan-in-fan-out)). Current active/total child and observation/correction budgets already bound the graph. Do not import an arbitrary universal concurrency number; choose limits from runtime, cost, risk, and project constraints.

4. **Evidence and status validity — strong coverage; digest authentication is the important edge (no gap).** The skills keep execution, liveness, observation health, progress, acceptance, and availability separate; timeouts do not imply failure; terminal labels do not prove acceptance; reports need native identity or canonical digest; and the contract correctly says a recomputed digest is integrity, not issuer authentication. OpenAI's subagent docs similarly distinguish a completed coordination action from subagent completion and direct the parent to combine results ([Multi-agent guide](https://developers.openai.com/api/docs/guides/agents-api/multi-agent)). No change indicated beyond retaining that issuer/provenance distinction.

5. **Capability discovery — covered; runtime descriptions should remain authoritative (no gap).** The skills require inspecting live tool descriptions/metadata, provider-native exact-ID routes, and documented capability detection; they forbid invented generic routes and distinguish backing kinds. This aligns with OpenAI's documented differences between orchestration modes and platform primitives ([Agents API multi-agent](https://developers.openai.com/api/docs/guides/agents-api/multi-agent)). Static examples or cross-provider analogies must not override the active tool contract.

6. **Authorization — comprehensive (no gap).** New-task creation, descendants, repository writes, transfers, integration, and lifecycle operations have separate boundaries. Explicit no-create and dry-run/review cases are honored. OpenAI's security guidance supports minimizing unnecessary capability and gating consequential actions, but does not prescribe the skills' exact approval model ([prompt-injection design](https://openai.com/index/designing-agents-to-resist-prompt-injection/)). Keep the distinction between technical capability and user authorization.

## Source scope and limits

OpenAI API/Codex materials are primary sources for their own agent primitives and security advice. Temporal and Microsoft Durable Functions document durable workflow mechanics, not user-visible agent-thread policy; their retry and fan-out models are analogies only. None establishes universal limits, approval thresholds, or evidence formats for these skills. Reviewed 2026-09-30.
